## Feature 1: Attendance Delete & Activity History

### Server — `server.ts`

**1. New endpoint `DELETE /api/attendance/:id`** (add right after the PUT at line 1020), following the existing dual-DB pattern:
- **PG branch:** SELECT the record first (404 if not found) → look up the deleting user's display name via `SELECT name, role FROM users WHERE id = req.user.id` (JWT's `req.user` has id/email/role but no name; fall back to email) → `DELETE FROM attendance WHERE id = $1` → INSERT an `audit_logs` row: `user_name` = display name, `action` = `'Attendance Record Deleted'`, `details` = JSON string `{actorRole, target, oldValue, newValue, reason, status}`.
- **JSON branch:** findIndex (404 if missing) → capture record → splice from `db.data.attendance` → build the rich frontend-shaped `AuditLog` object (administrator, actorRole, action, target, oldValue, newValue, status — same shape the UI displays) and unshift into `db.data.auditLogs` → `db.write()`.
- Return `{ success: true, data: { deletedRecord, auditLog } }`.

**2. Make audit logs round-trip so they survive reloads.** (Important: on boot `loadDatabaseData` replaces client audit state with `GET /api/audit-logs` — App.tsx line 446 — so today's client-only log entries are silently wiped on every reload. Server-side persistence is required for the requirement to hold.)
- `POST /api/audit-logs`: map rich object → `user_name = item.administrator || item.user`, serialize the extra fields (`actorRole, target, oldValue, newValue, reason, ipAddress, status`) into `details` as JSON. JSON branch stores the object verbatim.
- `GET /api/audit-logs`: after fetching, map PG rows back to the rich shape (`administrator` from `user`, JSON.parse `details` and merge); legacy/minimal rows degrade gracefully instead of rendering blank.

### Frontend

**3. `src/services/api.ts`** — add `deleteAttendance: (id) => authFetch('/api/attendance/' + id, { method: 'DELETE' })` in the Attendance block (line ~103).

**4. `src/components/attendance/AttendanceTable.tsx`** — add per-row delete:
- New optional prop `onDeleteRecord?: (recordId: string) => void`.
- New "Actions" column (trash-icon button) rendered only when the prop is provided and `currentUserRole` is `admin` or `super_admin` (per user decision; employees never see it). Button triggers `window.confirm(...)` then calls `onDeleteRecord(rec.id)`. Empty-state `colSpan` updated 7 → 8.

**5. `src/App.tsx`** — make deletes real and logged:
- Pass `onDeleteRecord={handleDeleteAttendanceRecord}` to both `<AttendanceTable>` usages (Dashboard ~line 2055 and Attendance section ~line 2069).
- Rewrite `handleDeleteAttendanceRecord` (line 1415) as async: guard employee role → find record → `await api.deleteAttendance(recordId)` → on success remove from state, prepend the **server-returned** auditLog (fallback: build locally in the existing format) and toast; on API failure keep the record and show an error toast. The `ManualCorrectionModal` "Danger Zone" delete becomes persistent automatically since it calls this same handler.

## Feature 2: Check-in-only manual entry + Dashboard checkout updates the same record

**6. `ClockInModal.tsx`** — default `exitTime` state to `''` instead of `'05:30 PM'` (field is already non-required), with a "leave blank if still on shift" hint. Downstream already handles it: `exitTime || null` (App.tsx:1223) and `calculateWorkHours` returns 0 hrs for null exit (App.tsx:96).

**7. `ManualCorrectionModal.tsx`** — make exit optional on edit too: remove `required` + `*` from "Corrected Exit Time"; when loading a record with no exitTime set state to `''` instead of `'05:30 PM'` (both the `useEffect` at line 47 and `handleRecordChange` at line 62).

**8. `App.tsx` `handleDirectCorrectionSubmit`** (line 1345) — store `exitTime: data.exitTime || null` in both the state update and API payload; audit `newValue` shows "Active" when blank.

**9. `App.tsx` `handleDirectAttendanceSubmit`** (line 1199) — toast wording: when no exit time, say "check-out pending" instead of "0 hrs logged".

**10. `App.tsx` `handleCheckOutPortal`** (line 386) — so the Dashboard Check Out reliably updates the same (manually created) record:
- Broaden record matching to the same logic the Dashboard widget uses (employeeId match OR name match) instead of strict `a.employeeId === empId`.
- Show an error toast instead of silently returning when no same-day check-in exists.
- Skip overwrite if the record already has an exitTime.

The existing `EmployeeCheckInWidget` already shows "Checked In at X" + a "Check Out Now" button whenever today's record has entryTime and no exitTime, so a check-in-only manual record flows straight into this path.
